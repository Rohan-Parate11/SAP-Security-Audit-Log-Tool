# CLAUDE.md

Instructions for Claude Code sessions working in this repository.

## What this is

SAL (Security Audit Log Tool) - a Flask + vanilla-JS internal tool that
connects to live SAP systems over RFC, collects SAP Security Audit Log
(SM20) events, runs deterministic detection rules against them, and gives
security analysts a dashboard/findings workflow. Detection-only - nothing
in this codebase writes back to SAP or takes remediating action, ever.

Read `Docs/ARCHITECTURE.md` first for the module map and data flow.
Read `Docs/PROJECT-CONTEXT.md` for current phase status and key constraints.
Read `Docs/Open_Questions_For_Review.txt` for decisions still pending from
the project owner. All project documentation (PRD, architecture, rules,
phase roadmap, design system, durable decision memory, changelog, the
original blueprint docs, and the training guides below) lives under
`Docs/` - this is the one place to look.

(`requirements-dev.txt`) - doc tooling only, not imported by `sal/`.

## Commands

```bash
python run.py                        # dev server, http://127.0.0.1:5050
python -m pytest tests/ -q            # full test suite
python scripts/collect_sm20.py <SYSTEM> <CLIENT> <DAYS_BACK>   # manual CLI backfill
```

No build step for the frontend (no bundler, no npm) - `sal/web/static/js/app.js`
and `style.css` are served as-is.

## Non-negotiable constraints

- **Never store a SAP credential in the database.** Passwords live only in
  `.env` (`SAL_SAP_<SYSTEM_ID>_PASSWD`). The `systems` registry table has
  no password column by design - don't add one.
- **Never write back to SAP.** Read-only, always.
- **No external CDN dependencies in the frontend.** No CDN fonts, icon
  libraries, or JS. This runs against a live, often network-locked-down
  SAP environment - everything must be self-contained.
- **Don't assume an SAP RFC/function-module name from documentation
  alone.** This project has been burned twice by exactly that
  (`RSAU_READ_LOG` looked right and silently returned zero rows;
  `RSAU_API_GET_LOG_DATA` is what actually works). Validate against a
  live system before committing to one in a plan or in code.

## Conventions to follow

- Raw `sqlite3`, no ORM (`sal/storage/db.py`). Deliberate at this scale.
- One small, focused module per concern (`findings.py`, `jobs.py`,
  `systems.py`, `sla.py`, `export.py`) - don't grow one file to cover
  multiple concerns.
- Every function that makes a live RFC call needs `try/except/finally`
  discipline around any state it finalizes (a `collection_runs` row got
  stuck at `"running"` forever once, from a narrower `except` clause that
  didn't cover every failure mode - see `sal/collectors/sm20.py`'s
  `collect_and_store()` for the corrected pattern).
- Don't force a dateless/single-call operation through `sal/jobs.py`'s
  chunked multi-day job runner just for "consistency" - that machinery
  solves a problem (day-range chunking, resumability, progress/ETA) that
  a single RFC call doesn't have. Give it its own simple, direct,
  synchronous path with an explicit timeout instead.
- Tests live in `tests/`, using `conftest.py`'s `isolated_db` autouse
  fixture (redirects storage to a throwaway file - never touches the real
  `data/sal.db`). RFC-calling code is tested by monkeypatching the
  collector, not by hitting live SAP.
- Update `Docs/CHANGELOG.md` for any user-visible or architecturally
  significant change.

## Workflow this project actually follows

See `.claude/skills/sal-phase-workflow/SKILL.md` for the full, repeatable
process used for every phase/feature so far: plan → dev-team review →
council (only for genuine unresolved tensions) → implement with tests →
`python-reviewer` + `security-reviewer` → `a11y-architect` for any new UI
→ live browser verification → changelog entry. Follow it for new phase
work unless the user directs otherwise.

## Security posture (current, deliberate, pilot-scale)

No RBAC - `_current_actor()` is a self-declared display-name cookie,
attribution only. SAL_RFC (the SAP technical user used for all collection
paths) currently has SAP_ALL; a scoped read-only role is planned but not
built. Don't "fix" either of these unilaterally - they're tracked, known
decisions (`Docs/Open_Questions_For_Review.txt`), not oversights.
